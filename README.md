## Сценарио

| Хэсэг | Performance | Reliability | Availability | Report |
|---|---|---|---|---|
| Тойм | Сагсанд бараа нэмэх | Төлбөр хийх | Сервер унасны дараа сэргэх | Тайлан авах |
| Системийн төлөв | API ажиллаж байгаа | API ажиллаж байгаа, 5% санамсаргүй 500 | API ажиллаж байгаад унана | API ажиллаж байгаа |
| Орчны төлөв | localhost, 20 VU, 1 мин | localhost, 20 VU, 1 мин | localhost, 20 VU, 2 мин | localhost, 20 VU, 1 мин |
| Гадаад өдөөлт | Хэрэглэгч POST /cart/add илгээнэ | Хэрэглэгч POST /pay илгээнэ | Тестийн 30 дахь секундэд процессыг зогсоож, 10с дараа асаана | Хэрэглэгч GET /report илгээнэ |
| Шаардлагатай хариу | 200, бараа нэмэгдэнэ | Амжилттай төлбөрт 200 | Дахин асахад 200 хариулж эхэлнэ | 200, тайлан буцна |
| Хэмжүүр | p95 < 20 мс | Алдааны хувь < 8% | Амжилттай хүсэлт ≥ 90%, сэргэх хугацаа ≤ 12с | p95 < 450 мс |

VU бүр cart → report → pay гэж хүсэлт явуулаад 1с амарна. Хэвийн үед ойролцоогоор 46 хүсэлт/с; энэ нь тогтмол RPS бус, 20 VU тогтмол ачаалал. Алдаа ба хүртээмжийг хувь, хугацааг p95-аар хэмжинэ. Сценарионууд нь бодит үйлдэлтэй, хэрэглэгчид хэрэгтэй, endpoint ба ачаалал нь тодорхой, босго нь тоон, шалгах алхам нь ойлгомжтой.

## SLO

| Сценарио | SLI | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | cart latency | p95 < 20 мс | 20 VU, 1 мин |
| Reliability | pay error rate | < 8% | 20 VU, 1 мин |
| Availability | Амжилттай хүсэлт / нийт хүсэлт | ≥ 90% | 20 VU, 2 мин, 10с зогсолт |
| Report | report latency | p95 < 450 мс | 20 VU, 1 мин |

Cart-д localhost-ийн бага саатлыг бодож 20 мс, pay-д суулгасан 5% алдаанд хэлбэлзлийн зай өгч 8%, report-ын 200–400 мс сааталд 450 мс сонгов. Availability-ийн 90% босго нь 10с зогсолтыг 2 минутад багтаах зорилготой; цагаар бодсон budget = 120 × (1 − 0.90) = 12с. Сэргэх хугацааг `run-lab.py` процессыг зогсоосноос эхний 200 хариу хүртэл хэмжиж, ≤ 12с эсэхийг шалгана.

## Ажиллуулах

```bash
npm ci
python3 run-lab.py pass
python3 run-lab.py fail
python3 run-lab.py chaos
```

WSL дотор k6, Node.js, Python 3 суусан байна. Скрипт локал API-г өөрөө асааж, тест дуусахад зогсооно. Chaos нь 2 минут үргэлжилж, 30 дахь секундэд серверийг унтраагаад 10с дараа асаана. Орчны хувилбарууд [environment.txt](results/environment.txt)-д бий.

## Үр дүн

| Тест | cart p95, мс | report p95, мс | pay алдаа | Амжилттай хүсэлт | k6 exit |
|---|---:|---:|---:|---:|---:|
| [PASS](results/pass.txt) | 2.1952 | 391.6527 | 4.6237% | 2747 / 2790 = 98.4588% | 0 |
| [FAIL](results/fail.txt) | 1.7376 | 390.8278 | 4.8491% | 2739 / 2784 = 98.3836% | 99 |
| [Chaos](results/chaos.txt) | 1.9626 | 388.5665 | 19.4357% | 4817 / 5742 = 83.8906% | 99 |

PASS тестэд дөрвөн threshold биелсэн. Нийт хурд 45.543632 хүсэлт/с байв. `pay 200` check дээр алдаа байгаа ч төлбөрийн error rate зөвшөөрсөн 8%-аас бага тул reliability SLO биелсэн.

FAIL хувилбар үндсэн тестээ ашиглаж, зөвхөн report-ын босгыг `p(95)<100` болгосон. Сервер дор хаяж 200 мс хүлээдэг учраас энэ босго биелэхгүй. Харин cart-д 50 мс тавибал localhost-ийн хариу түүнээс хурдан тул PASS хэвээр үлдэнэ.

Гаралтын `✗ 'p(95)<100' p(95)=390.82ms` мөр FAIL-ийг харуулна. k6 exit code **99** буцаасан; CI энэ тэгээс ялгаатай кодоор build-ийг зогсооно. Кодыг Python шууд процессоос авдаг тул `tee`-ийн 0 кодтой андуурахгүй.

Chaos үед cart, report-ын хугацааны threshold PASS, availability ба reliability FAIL болсон. Нийт алдаа 925 / 5742. Хүсэлтээр бодсон budget = 5742 × 0.10 = 574.2 буюу бүхэл хүсэлтээр 574 алдаа; бодит алдаа 351-ээр илүү байв. Серверийг 10с хүлээгээд асаасан ч эхний 200 хариу хүртэл 13.965с болсон тул 12с сэргэлтийн босго мөн зөрчигдсөн.

Цагийн budget ба хүсэлтийн budget адил биш: сервер унахад connection refused шууд буцаж, report-ын хүлээлт алга болдог тул VU бүр секундэд олон хүсэлт явуулна. Дээр нь pay-ийн санамсаргүй 500 алдаа нийт амжилтын хувийг бууруулна. Энэ туршилтад асаалтын хугацааг тооцоогүй 90%-ийн availability зорилт хэт өөдрөг байлаа. Availability-г тусдаа health probe-оор, reliability-г серверт хүрсэн төлбөрүүдийн 5xx хувиар хэмжвэл хоёр SLI-г салгаж болно.

## Дүгнэлт

Сценариог код болгоход хамгийн хэцүү нь хэмжүүрийн нөхцөлийг тодорхойлох байв. Ачааллаа 20 VU гэж тогтоогоод, RPS нь хариуны хугацаанаас хамаардгийг ажиглав. Хэвийн үед дөрвөн босго биелсэн. Төлбөрийн санамсаргүй алдаа байгаа нь тест заавал FAIL болно гэсэн үг биш. Chaos үед нэг уналт availability, reliability хоёрыг зэрэг зөрчсөн. Арван секунд хүлээхээс гадна сервер асах хугацааг тооцох хэрэгтэй байв. Иймээс туршилт availability-ийн тавьсан зорилтыг баталсангүй. Report-ын босгыг зориуд багасгахад k6 алдааны код буцааж, CI-д ашиглаж болохыг шалгав.
